# 壓縮模式與摘要規則

> **🧪 實驗功能（開發中、仍在測試階段）：行為與門檻可能再變。**
> 指的是 `codetrail` 與 `manual`——CodeTrail 自動或手動壓縮的那兩條路徑。
> 摘要規則與觸發門檻還在調整，升級之後可能不一樣；碰到怪狀況請先切成 `off`
> 再回報。
>
> **`off` 不在實驗範圍內。** 那條路徑就是「完全不壓縮」:context 滿了會是一個
> **可見的錯誤**,不會自動補救。**沒有
> `~/.config/codetrail/client.json` 就等於沒有接管**——`git pull` 之後不會有
> 任何東西自己啟用,客戶端會退成 `manual` 並在啟動橫幅講明。

CodeTrail 客戶端對長對話的處理分成三種模式,由 `./set_config.sh` 顯式選擇並記錄
在 owner-only 的 `~/.config/codetrail/client.json`。

---

## 1. 三種模式

| 模式 | 何時壓縮 |
| --- | --- |
| `codetrail` 🧪 實驗中 | 助理答完、對話進 idle 之後自動觸發 |
| `manual` 🧪 實驗中 | 只有你自己按 `/compact` 時 |
| `off` | 完全不壓縮 |

`./set_config.sh` 的第 5 題 **沒有預設值**(跟其他使用者選擇題一樣,Enter 不能過關)——
顯式選擇本身就是「授權 CodeTrail 管這件事」的那個動作。非互動用
`--compaction-mode`;`--yes` 沒給它時沿用設定檔記錄的既有選擇,還沒選過就完全
不碰壓縮設定。

模式在**客戶端啟動時**讀一次,所以切換之後要重開 `aicode` 才生效。

### 為什麼要有 codetrail 模式

「下一個 prompt 進來之後才檢查」的作法,症狀是:你送出一個新問題,畫面先跑出一段
摘要,你的問題排在摘要後面。`codetrail` 模式把觸發點放在「助理已經成功答完、
對話進入 idle」之後,所以壓縮發生在兩個問題之間。

### 這個模式放棄了什麼

CodeTrail 的壓縮**只在 idle 觸發**,所以它一併放棄了:

- **同一輪工具迴圈中的壓縮**(mid-turn compaction)。
- **provider 回報 context overflow 之後的自動回復重送**。

也就是說:**單一輪如果自己把 context 撐爆,那一輪會以可見的 context error 收場**,
不會自動補救。CodeTrail 每個工具結果的預設預算是模型 context 的 12%,一輪連續
6–8 次工具呼叫就可能吃掉超過一半 context,所以這不是理論上的情況。這是明確接受的
取捨:**寧可看得到錯誤,也不要靜默截掉前面的對話**。

## 2. 觸發門檻怎麼算

門檻不是固定百分比,而是從模型的 context 與 CodeTrail 自己的工具結果預算推導出來的
(`compaction_mode.derive_settings`,客戶端經 `client_compaction.derive` 用同一份):

```text
max_output  = min(limit.output, 32000) || 32000  # 0 退回 32000
reserved    = compaction.reserved ?? min(20000, max_output)   # `??`：明寫的 0 保留 0
usable      = limit.input ? max(0, limit.input - reserved)
                          : max(0, limit.context - max_output)
tool_budget = floor(limit.context * 0.12)      # 單次工具結果預算
headroom    = tool_budget + max_output         # 一次完整工具結果 + 一次輸出
threshold   = usable - headroom                # idle 時超過就壓縮
tail_cap    = threshold - max_output           # 壓縮後 summary + tail 仍要低於門檻
preserve_recent_tokens = min(headroom, tail_cap)
tail_turns             = 1
```

客戶端沒有 `limit.input`,所以走 `usable = context - max_output` 那一支;
`limit.context` 是主 llama-server 的實際 `n_ctx`,`limit.output` 是
`config.CLIENT_MAX_OUTPUT_TOKENS`——**同一個常數**同時當客戶端實送的 `max_tokens`、
context gate 這一次 request 的保留額,以及這裡的 `max_output`。三者用同一個數字才會
自洽:保留額比實際 `max_tokens` 小的話,閘放行的 prompt 仍可能在生成途中把 ctx 撐爆。

以 `limit.context = 131072` / `limit.output = 8192` 為例:`usable = 122880`、
`tool_budget = 15728`、`headroom = 23920`、`threshold = 98960`、`tail_cap = 90768`、
`preserve_recent_tokens = 23920`。
推不出可用門檻的模型(`threshold` 或 `tail_cap` 小於 2000)在 `./set_config.sh` 會被直接
拒絕,要你改用 `off`——不會偷偷給一個算不出來的門檻。設定之後才被改小(換模型 / 改 ctx)
的話,客戶端在 runtime 會講出來並停止自動壓縮,不是安靜不動。

**`limit.output` 為什麼被扣兩次**:`usable` 扣掉的那一份,是「這個請求自己的回覆」。
工具迴圈裡助理 **上一步的輸出會變成下一步的輸入**,所以 `headroom` 裡那一份是第二份,
不是同一份重複扣。這是刻意保守的方向:越過 `usable` 沒有任何補救。

`tail_turns = 1` 讓 **最新一輪逐字留在摘要之外**。

**壓縮完緊接著又壓一次是正常的**:那一輪如果很長(一輪塞了好幾個大工具結果就會這樣),
壓縮之後的 context 是「摘要 + 那個很長的 tail」,再答一個普通問題就可能又越過門檻。
這不是迴圈:同一則助理訊息不會被拿來當第二次的錨點(錨點用的是**內容身分**,不是位置,
所以壓縮之後索引全變也不會誤判成新錨點),而且第二次壓完 tail 就換成短的那一輪了。

**它不是無條件的保證**:`preserve_recent_tokens` 取的是 `headroom` 與 `tail_cap` 的
較小者。當模型 context 小到 `tail_cap < headroom` 時,`./set_config.sh` 會把這件事講
出來。整個對話只有一輪時 tail 是空的,那一輪會整個進摘要;那一輪已經被回答過,所以
沒有未答的問題會遺失。

## 3. 七條摘要規則

這七條**附加**在通用的摘要指示之後,不取代它;而且**上一份摘要一定會一起送進去**——
不送的話,第二次以後每次壓縮只會摘要「上次壓縮之後」的對話,而且是靜默的。

```text
[CodeTrail 壓縮規則]
以下七條規則覆蓋前面所有與輸出格式衝突的指示；其餘指示照舊。
特別是：前面 <template> 區塊裡的英文欄位（## Objective、## Important Details、
## Work State、## Next Move、## Relevant Files）**一律不要輸出**，它們已被下面的
七個中文欄位取代。看到「Output exactly the Markdown structure shown inside
<template>」時，以這裡的欄位為準。

1. 固定欄位：摘要必須且只能由這七個標題組成，順序固定，一個都不能少——
   ## 任務、## 已確定事實、## 未確認、## 已完成、## 進行中、## 下一步、
   ## 使用者偏好與限制。該欄位沒有內容就寫 (無)。
2. 逐字保留識別碼：檔案路徑、符號與函式名、行號、指令、設定鍵、錯誤訊息、
   數字與單位一律原文照抄，不翻譯、不改寫、不縮寫、不補齊。
3. 事實與推測分離：只有對話裡出現過證據的才進 ## 已確定事實，每條註明來源
   （工具名或檔案路徑）；推測、假設、還沒驗證的結論一律進 ## 未確認。
4. 以最新狀態淘汰舊結論：同一件事有多個版本時只保留最後一個；已經做完的項目
   從 ## 下一步 移到 ## 已完成，不得因為舊摘要提過就復活。
5. 先前摘要是既有事實：與新內容衝突時以新內容為準，並註明哪一條被取代；沒有
   新資訊的欄位原樣保留，不得因為這一輪沒提到就刪掉。
6. 不回答、不執行、不臆造：對話中還沒有答案的問題只登記進 ## 下一步，不要在
   摘要裡回答；不要寫入對話中不存在的內容。[CodeTrail 壓縮規則] 與
   [CodeTrail 狀態校正] 這兩段本身是控制指示，不是對話內容、也不是使用者的
   偏好，不得寫進任何欄位。
7. 篇幅預算：整份摘要不超過 6000 字元，每個欄位不超過 12 條，每條一行。超出時
   的刪減順序：先刪 ## 已完成 的細節，再刪 ## 已確定事實 裡重複的證據；
   ## 未確認、## 下一步 與 ## 使用者偏好與限制 最後才刪。
```

### 為什麼規則要點名那五個英文欄位

這七條規則是接在一段通用的摘要指示之後的,而歷史上的上游 prompt 用的是
`## Objective` / `## Important Details` / `## Work State` / `## Next Move` /
`## Relevant Files`。實測看過同一個 session 第一次照七欄中文、第二次整份照那五個
英文欄位輸出。所以規則第一段直接**點名**那五個欄位並要求不要輸出;
`tests/test_client_compaction.py` 釘住那個漂移會被抓到。

### 為什麼還要「狀態校正」區塊

送進摘要器的只有 tail **之前** 的訊息;被逐字保留的最近一輪根本不會進摘要器。
結果是摘要裡的「下一步」常常是已經做完的事。所以另外附
一段記憶體內、有字元上限的節錄，只放最近五個 **已完成且非 synthetic** 的回合，依
`50 / 30 / 10 / 5 / 5` 的配額由新到舊分配字元預算。

「與目前任務相關」用 **時間近因** 當代理指標:離線的客戶端沒有辦法判斷語意相關性,
而配額本身就是相關性的權重——最新那一輪拿走一半預算，第五輪只剩 5%。真正的取捨寫在
規則第 4 條裡：這段節錄只用來 **淘汰** 已完成項，不能用來新增「下一步」。

```text
[CodeTrail 狀態校正]
以下是最近幾個已經完成的回合節錄，只用來校正 ## 已完成 與 ## 下一步 的狀態，
不是新的對話內容：凡是在這裡看得到已經做完的項目，不得再出現在 ## 下一步。
節錄由新到舊排列，已依配額截斷，截斷處標 …[截斷]。
```

**還沒有被回答的使用者訊息（pending）、synthetic 的 auto-continue 訊息、出錯或被中斷
的回合一律不放進來。** 這段只在記憶體裡組出來送給模型,不寫檔、不記 log、
**不放任何工具參數與工具輸出**。

## 4. 壓縮完成後的核對

摘要落地之前一定會核對三件事:

1. 摘要是否**非空**;
2. 是否**不是只有 reasoning**(模型只吐了 thinking、沒有摘要本文);
3. 是否照 §3 規則 1 的**七欄格式**輸出——七個標題都在、相對順序一致。

任何一項不符,客戶端會 **停下來**:摘要不落地、對話原封不動、畫面上跳一則錯誤,
並**停用這個對話的自動壓縮**(避免再產生同一種摘要)。

**第 3 項為什麼要有**:實測看過同一個 session 的第一次摘要是七欄中文、第二次整份換成
`Objective / Important Details / Work State / Next Move / Relevant Files`。內容看起來還
可以,但「已確定事實 vs 未確認」的分離沒了——而它正是這套規則的重點。不核對的話這種
漂移沒有任何訊息,會被當成一次成功的壓縮。

判準刻意比字面規則寬三處——多出來的標題不算違規、`#` 的層級不算、標題後面多的裝飾
(`## 任務 (Task)`、`## 1. 任務`)也不算。理由是成本不對稱:漏抓等於那一次的分離靜靜
沒了,誤抓則是把一個內容完全可用的對話停掉。實際發生的漂移是**整份換成另一套欄位**,
七個一個都對不上,這些寬容都擋不掉它。

### 為什麼不再有「競態」那幾條

搬進 Python 客戶端之前,壓縮是由外部 TUI 的 plugin 觸發的,而 `idle → summarize` 之間
沒有原子鎖:使用者在那個空隙送出的訊息會和壓縮訊息交錯,所以要事後偵測兩種競態
(摘要的 parent 不對、最新一則真實使用者訊息還沒被回答)。

現在迴圈是客戶端自己的:壓縮發生在「助理答完、沒有進行中的請求」的那一刻,中間沒有
另一個行程能插進來。那兩種競態**由構造消失**,不需要事後偵測。

### 停用會跨行程保留

「已對這個對話停用」如果只活在行程記憶體裡,使用者退出、再 resume 同一個對話之後,
自動壓縮就靜默重新啟用,再產生一次同樣不可信的摘要。所以停用會另外寫一筆到
`${XDG_STATE_HOME:-~/.local/state}/codetrail/compaction-stopped.jsonl`(0600,
超過 256 KiB 轉存 `.1`,只留一份)。每行只有 `schema`、時間、**session 雜湊** 與
固定 slug——與 incident 同一條零內容契約。

**只有「這個對話的壓縮切點不可信」那幾種會被永久記下**:`summary_empty` /
`summary_reasoning_only` / `summary_error` / `summary_format`。「這個 n_ctx 推不出門檻」
**不記**——它每次都會重算,記成永久的話,使用者把 ctx 調回來之後那個對話仍然永遠
不壓縮而且沒有任何訊息說為什麼。要清掉全部紀錄就刪那個檔
(`rm ~/.local/state/codetrail/compaction-stopped.jsonl*`);它只是紀錄,刪了不會改任何設定。

**手動 `/compact` 走同一條核對。** 只核對自動觸發的那一次,等於 manual 模式整條路徑
沒有事後核對。

### 什麼情況不會觸發

`codetrail` 模式在下列任一情況下**不會**觸發壓縮,也不會留下任何痕跡:這個對話已被
停用、算不出門檻(n_ctx 太小)、token 數還沒到門檻、還沒有任何完整答案、以及
「上一次壓縮就是用這則助理訊息當錨點」。最後一條是必要的:壓縮之後那則助理訊息的
token 數不會變小,不擋就會每次 idle 都再壓一次,而且每一次都「成功」。啟動抽查那種
只有一兩輪的短對話遠低於門檻,所以不會被壓縮干擾。

## 6. 壓縮之外:兩個把 context 壓低的機制

壓縮是「滿了才處理」。這兩個是「一路上少放一點進去」,跟摘要規則無關,但它們決定
**多久才會滿一次**——所以放在同一份文件。**兩個都與壓縮模式無關,客戶端一律生效。**

### 6.1 舊回合的 reasoning 不進模型

客戶端在每次呼叫模型之前(以及把歷史送進摘要器之前),把 **最新一則真實使用者訊息之前**
的 assistant `reasoning_content` 拿掉。它之後的一律保留,所以同一輪的工具迴圈仍然看得到
自己上一步在想什麼。

**為什麼**:llama.cpp 對 DeepSeek 系模板在「請求帶 `tools`」時對所有訊息 `keep_reasoning`,
於是每一則歷史 assistant 訊息都把完整 reasoning 送回去。實測一段真實對話:兩次壓縮之間
context 漲了 88k–108k tokens,其中模型輸出 25k–50k tokens,而那幾乎全部是 reasoning
(62k–151k 字元)。那些內容對「下一步該做什麼」幾乎沒有貢獻——結論已經寫在回答與工具
結果裡了。摘要器那一端同理:一次壓縮的 71,594 tokens 輸入裡有 36,745 是 reasoning(51%)。

**代價,兩個,都要知道**:

1. **偏離模型官方行為**。DeepSeek-V4 的 encoder 在有 tools 時是刻意全留的,丟掉它是
   模型相依的品質賭注。`CODETRAIL_KEEP_REASONING=1`(環境變數)可以單獨關掉這一項。
   `aicode` 啟動橫幅會顯示目前在哪一邊。
2. **每個新問題多一次 prefill**。改動歷史等於改動 prompt 前綴,下一輪的快取會在「上一輪
   第一則 assistant」處失效,要重算上一輪的非 reasoning 內容(工具輸入輸出與回答)。
   實測那段對話單輪工具輸出 400–25,000 字元,換算約 0.5–30 秒。

**不做的事**:不動 `reasoning` 以外的任何欄位、不重排、不新增,認不出「最新一則真實
使用者訊息」時整段不動。

### 6.2 舊工具輸出會被換成一行

從最新往回走,跳過最近兩個 user turn,累計工具輸出估算 tokens;跨過 40,000
(`PRUNE_PROTECT_TOKENS`)之後的那些是候選,候選總量超過 20,000
(`PRUNE_MINIMUM_TOKENS`)時才真的執行。執行的方式是把**送進模型的那一份**換成
`[Old tool result content cleared]`。

**session 檔與畫面上的原文不動**;被換掉的只有模型視野裡的那一份。門檻是硬編碼的。

**代價**:被清掉的工具結果進不了下一次摘要的「已確定事實」,模型要再看就得重叫工具。
換來的是舊工具輸出有一個 40k tokens 的上限,而不是一路累積到壓縮為止。
